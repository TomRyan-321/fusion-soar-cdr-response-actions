# AGENTS.md

Notes for an AI agent (or person) standing this up again. The README covers what the workflow does; this file covers how to deploy and test it without relearning the traps.

## Stand it up

1. `cp .env.example .env` and fill in the Falcon API client (scopes: Workflow Read/Write, API integrations Read, Alerts Read) and `APPROVER_EMAIL` (must be a Falcon user in the tenant; the approval email goes to it and responses are only accepted from Falcon users).
2. In CrowdStrike Store, configure **AWS IAM, EC2, S3, Lambda, EFS, RDS, SNS, CloudTrail and GuardDuty**. Set Account ID to `{account_id}` to cover every account that has the same role name and external ID (the console accepts it when editing a config). It does **not** work for AWS IAM's generic `AWS IAM - …` actions (no account input) or for CloudTrail and GuardDuty (no account or region input; with `{account_id}` they fail with "Missing a valid account ID in config or execution" or "Something went wrong"). Give those a config per account (IAM) or per account and region (CloudTrail, GuardDuty); `deploy.py` tells `route.py` which exist, and routes fall back elsewhere.
   Deploy `cfn/extra-response-permissions.yaml` in each account: CrowdStrike's role template (`cs_aws_automated_response-1.8.yaml`, pulled by its root stack's StackSet) has no CloudTrail `StartLogging` or GuardDuty write permissions. Configs are console-only: for API clients `GET /plugins/entities/configs/v1` works, but POST/PUT/PATCH/DELETE return 405 and `/plugins/entities/api-spec-definitions/v1` returns 404.
3. `pip install crowdstrike-falconpy pyyaml`
4. `set -a; source .env; set +a; scripts/deploy.py`. It imports the four `CDR respond - …` child workflows, then the main workflow with their definition IDs filled in. If they already exist, import returns 409: use `scripts/deploy.py --replace`. `--self-contained` deploys the single-workflow version instead (all actions inline; `--replace` also removes the split version's children). Never run both versions at once: each detection would get two responses.
5. In a **test** AWS account: `scripts/simulate-detections.sh run`, wait 5–15 min, check executions, then `scripts/simulate-detections.sh cleanup`.

## Change and test loop

- **The workflow YAML is generated.** Edit `scripts/build-workflow.py`, `scripts/workflow/route.py` or `scripts/workflow/parse_llm.py`, then run `scripts/build-workflow.py`. If the workflow's shape changed, also run `docs/make-workflow-diagram.py` (canvas images in `docs/workflow/`) and update `docs/make-architecture.py`.
- **Routing or prompt change:** `scripts/replay-detections.py tests/sample-events.json`. It runs the routing and LLM steps on real detections from the last day plus the samples, and prints route, action, target, auto-run and tokens. Takes about 2 minutes and never acts on AWS. Add a sample when you add a routed API call.
- **Testing an AWS action:** after deploying, run the child workflow directly: `Workflows.execute(definition_id=<child id>, body={"action": ..., "target": ..., "detail": ..., "region": ..., "port": 0, "account_id": ..., "case_id": ..., "mode": "Test"})`. Use private or nonexistent `cdr-sim-*` targets; a "not found" from AWS still proves the inputs, config lookup and role. With a fake `case_id`, only the comment step fails.
- **End to end:** run the simulation. Scenarios that expose resources publicly (`PUBLIC`) or change GuardDuty (`CONTROLS`) are opt-in by name. The SCP in the test account denies `cloudtrail:CreateTrail`, so `StopLogging` has no scenario; only the org trail exists, so don't stop it. Rules 5012 (admin policy on a user), 5010 (on a group) and 204 (login profile) never raised an alert in testing, so those routes are only covered by `tests/sample-events.json`. CDR raises one alert per rule per UTC clock hour: a repeat in the same hour folds into that alert (even if closed) and the workflow doesn't fire. Run a scenario at most once per clock hour, ideally just after the hour.
- **Executions:** `Workflows.search_executions(filter="definition_id:'<id>'")` returns every step's `result` and `error_message`. `execution_results(ids=)` sometimes omits `resources`. The AWS step and its comment run in the child workflow: the main workflow's `Respond…` step result holds the child's `execution_id`, and when the child fails its `error_message` links to it.
- **Approvals can't be automated:** `Workflows.get_human_input(ids=<user_input_id>)` reads a pending approval (the ID is in the `RequestApproval` step's `result.result.user_input_id`), but `update_human_input` returns 403 `API clients cannot interact with human-inputs with a list of allowed responders specified`. Approve or decline from the email.
- **Cancel a run waiting on approval:** `execution_action(action_name="cancel", ids=<one id>)`. Only one ID per call.
- **Delete a workflow:** FalconPy has no wrapper; use `Workflows.override(method="DELETE", route="/workflows/entities/definitions/v1", parameters={"ids": id})`.

## Fusion YAML rules learned the hard way

- `import_definition` only shallow-validates. Real validation happens on enable, which returns **200 with errors** and leaves the workflow disabled. Always check `body.errors`.
- `version_constraint`: `~1` for core actions (variables, case, comment, Python, approval email, trigger); `~0` for the Charlotte AI actions; none for Store app actions (AWS IAM/EC2, Cloud Detection Parser). Wrong value gives "activity not found".
- Outputs of actions that have a `legacy_namespace` in the activity catalog (Charlotte AI actions) are referenced as `${Node.FaaS.<namespace>.<field>}`; everything else as `${data['Node.field']}`. Inside a CEL expression, everything (including `WorkflowCustomVariable.X`) must be `data['…']`.
- Python script runtime must be `py0313general`. `python3` enables fine and then fails at runtime.
- The LLM Completion action ignores `json_schema` for Claude models; ask for bare JSON in the prompt and extract it in Python.
- "Triage Detection with Charlotte AI" doesn't support CDR detections (IDP and EPP only).
- Cloud Detection Parser `rule_name` must be a playbook name (`sg-revoke-ingress`, `remove-public-snapshot`, `iam-role-apply-deny-policy`, `iam-disable-access-key`, `catch-all`, ...), not the detection name. A CEL expression works.
- Approval ("Request human input - Send email") needs `to`, `responders`, `user_input_timeout`, and conditions directly on `RequestApproval.result.user_response` whose values match `allowed_responses`.
- Several branches can point at one node or condition; Fusion inserts a join, and skipped branches don't block it. That's how the routed and LLM paths share the case, and the auto and approved paths share the action steps.
- **Calling a child workflow:** an on-demand workflow is an action whose `id` is its definition ID (no `version_constraint`), with its trigger parameters as `properties`. It runs synchronously. Integer inputs accept an integer variable. The ID changes on every re-import, so deploy fills in `__WORKFLOW_<file>__`.
- **On-demand inputs:** in templates use `${data['name']}`; in conditions use the bare name (`action:'x'`, or `action:['a','b']` for any of several). `${Trigger.name}` fails enable with the generic error.
- Inputs with dotted names (`params.query.UserName`, `json.ReservedConcurrentExecutions`) must be nested YAML objects. The generic `AWS IAM - …` actions have no `account_id`; the account comes from the IAM app config.
- Store app config `app_id` is often not the prefix of the app's action IDs; `deploy.py` holds the mapping. To identify an unknown config, run a read-only action with it: the wrong app returns 404 "config for definition ID <app id>".
- The trigger's `Detection.DetectionID` contains the rule ID (`…:fcs:ioa-224:…`), but some rules (for example `ioa-4020`, SSH open to the internet) aren't in the published policy list. Route on the CloudTrail `eventName` instead. Rules that no single API call identifies (hacking-related OS, ScoutSuite, CloudBerry, admin role on an instance) are matched on `${Trigger.Detection.Name}`; if CrowdStrike renames one, it falls back to skipped. Keep the sample's `name` equal to the real detection name.
- A response action can itself raise a CDR detection (attaching `AWSDenyAll` fires "admin policy attached to role"). Route skips anything done by `CrowdStrikeAutomatedResponse` so the workflow never undoes its own containment.
